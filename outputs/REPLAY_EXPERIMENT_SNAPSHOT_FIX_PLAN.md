# Replay 실험 스냅샷 일치 수정 계획

## 1. 문서 목적

정책 비교 결과에서 `실행 재생`을 선택했을 때 Replay가 완료된 실험의 입력이 아니라 현재 편집 중인 시나리오와 정책을 사용하는 문제를 독립적으로 수정한다.

이 문서는 구현 전에 문제의 범위, 목표 동작, 검증 조건을 고정하기 위한 작업 계획이다. 이 작업에서는 정책 확장 구조를 변경하지 않는다.

## 2. 현재 동작과 문제

`src/ui/App.tsx`는 다음 두 상태를 별도로 유지한다.

- 현재 편집 중인 `scenario`, `policies`
- 마지막으로 완료하거나 불러온 `result`

결과 카드는 `result.results`를 렌더링하지만 Replay 요청은 카드가 가리키는 결과가 아니라 현재 편집 상태를 사용한다.

```ts
client.current!.replay(scenario, policies[policyIndex], 0, ...)
```

또한 Replay 창에 전달하는 전체 PR 수도 `scenario.prCount`에서 가져온다.

```tsx
<RunReplay totalPrs={scenario.prCount} ... />
```

따라서 실험 완료 후 사용자가 시나리오 값이나 정책 설정을 편집하거나, JSON에서 결과와 다른 현재 설정을 함께 불러오면 다음 불일치가 발생할 수 있다.

- 결과 카드와 Replay가 서로 다른 시나리오를 나타낸다.
- 결과 카드와 Replay가 서로 다른 정책 설정을 나타낸다.
- Replay의 이벤트와 화면에 표시되는 전체 PR 수가 다를 수 있다.

## 3. 목표 동작

결과 카드에서 시작한 Replay는 해당 카드를 만든 `ExperimentResult`의 스냅샷만 사용해야 한다.

- 시나리오: `result.scenario`
- 정책: 선택한 `result.results[policyIndex].policy`
- 반복 번호: 현재 기능을 유지하여 `0`
- Replay의 전체 PR 수: `result.scenario.prCount`

Replay를 시작한 뒤 현재 편집 상태가 바뀌더라도 진행 중인 Replay의 입력과 표시 기준은 바뀌지 않아야 한다.

동일한 시나리오, 정책, 반복 번호는 결정론적으로 같은 실행을 생성하므로 Replay는 해당 실험의 첫 번째 시행과 일치해야 한다.

## 4. 포함 범위

1. 결과 카드에서 선택한 정책과 결과 스냅샷을 Replay 요청까지 정확히 전달한다.
2. Replay 요청이 현재 편집 상태 대신 완료된 실험의 시나리오와 정책을 사용하도록 수정한다.
3. Replay 창의 `totalPrs`가 Replay에 사용한 시나리오에서 오도록 수정한다.
4. 실험 완료 후 현재 시나리오와 정책을 변경한 상태를 재현하는 회귀 테스트를 추가한다.
5. JSON으로 불러온 `ExperimentResult`에서도 같은 기준을 적용한다.
6. Replay 반복 번호가 명시적으로 `0`임을 테스트 또는 코드에서 분명히 유지한다.

## 5. 제외 범위

- Replay에서 N개 시행 중 임의의 반복 번호를 선택하는 기능
- Replay 이벤트 저장 방식 변경
- 정책 인스턴스 식별자 도입
- 정책 등록 레지스트리 도입
- 정책 설정 UI의 동적 생성
- 저장 스키마 버전 또는 마이그레이션 체계 변경
- JSON 내보내기 파일에 서로 다른 현재 설정과 과거 결과를 함께 담을 수 있는 기존 동작의 전면 재설계
- 시뮬레이션 엔진, 정책 알고리즘, 지표 계산 변경

## 6. 설계 원칙

### 6.1 결과 스냅샷이 Replay의 단일 기준이다

Replay 클릭의 출처는 `PolicyComparison`에 전달된 `result`다. Replay 실행에 필요한 시나리오와 정책은 이 결과 객체에서 파생해야 하며, `App`의 현재 편집 상태에서 다시 조회하지 않는다.

### 6.2 배열 인덱스의 사용 범위를 클릭 시점으로 제한한다

현재 결과 UI는 정책 인스턴스 식별자가 없으므로 정책을 인덱스로 선택한다. 이번 작업에서는 인스턴스 ID를 새로 도입하지 않는다. 대신 클릭 시점에 해당 인덱스로 결과의 정책을 확정하고, 비동기 Replay 실행 중 현재 `policies` 배열을 다시 참조하지 않는다.

### 6.3 Replay 표시 정보도 같은 입력을 사용한다

이벤트 생성에 사용한 시나리오와 `RunReplay`의 표시 기준이 분리되지 않도록 Replay용 전체 PR 수를 별도 상태 또는 Replay 요청 컨텍스트로 보존한다. Replay 완료 후에만 존재하는 `lastReplay`에 의존하면 스트리밍 중 표시할 수 없으므로 시작 시점부터 사용할 수 있어야 한다.

### 6.4 기존 재현성을 보존한다

반복 번호 `0`과 엔진 호출 방식은 유지한다. 난수 시드 생성, 난수 소비 순서, 이벤트 순서에는 손대지 않는다.

## 7. 예상 변경 위치

- `src/ui/App.tsx`
  - Replay 입력을 실험 결과 스냅샷에서 선택
  - Replay 표시용 전체 PR 수 보존
- `src/ui/PolicyComparison.tsx`
  - 필요하다면 콜백 계약을 인덱스보다 명확한 Replay 대상 전달 방식으로 조정
- `src/ui/App.test.tsx` 또는 신규 UI 테스트
  - 현재 편집값과 결과 스냅샷이 다른 회귀 사례 검증
- 필요한 경우 `src/ui/PolicyComparison.test.tsx`
  - 선택한 결과 정책이 콜백에 정확히 전달되는지 검증

실제 구현 과정에서 더 작은 변경으로 목표를 달성할 수 있다면 파일 수를 늘리지 않는다.

## 8. 구현 단계

1. UI 테스트에서 Worker 또는 `SimulationClient`를 제어할 수 있는 테스트 경계를 마련한다.
2. 완료된 실험 결과와 현재 편집 상태가 서로 다른 테스트 fixture를 만든다.
3. 결과 카드의 Replay를 클릭했을 때 다음 인자를 검증하는 실패 테스트를 먼저 추가한다.
   - `result.scenario`
   - 선택한 `result.results[index].policy`
   - 반복 번호 `0`
4. Replay 선택 컨텍스트를 결과 스냅샷에서 파생하도록 구현한다.
5. `RunReplay.totalPrs`가 같은 스냅샷의 `prCount`를 사용하는지 검증한다.
6. JSON으로 불러온 결과에서도 동일한 경로를 사용하는지 기존 import 흐름을 확인한다.
7. 관련 테스트와 필수 검증을 실행한다.

## 9. 완료 조건

- [ ] 실험 완료 후 현재 시나리오를 수정해도 Replay 요청에는 완료된 실험의 시나리오가 전달된다.
- [ ] 실험 완료 후 현재 정책 설정을 수정해도 Replay 요청에는 선택한 결과 카드의 정책이 전달된다.
- [ ] 여러 결과 카드 중 선택한 인덱스에 해당하는 `result.results[index].policy`가 사용된다.
- [ ] Replay 반복 번호는 `0`이다.
- [ ] Replay 창의 전체 PR 수는 Replay 입력 시나리오의 `prCount`와 일치한다.
- [ ] Replay 시작 후 현재 편집 상태 변경이 진행 중 Replay의 기준을 바꾸지 않는다.
- [ ] 시뮬레이션 엔진의 이벤트와 난수 소비 순서는 변경되지 않는다.
- [ ] 회귀 테스트가 문제 상황을 명시적으로 재현한다.

## 10. 검증 명령

UI 흐름을 변경하므로 저장소 지침에 따라 다음을 실행한다.

```text
pnpm lint
pnpm typecheck
pnpm test
pnpm build
pnpm test:e2e
```

엔진 성능을 변경하지 않으므로 `pnpm benchmark`는 필수 범위가 아니다.
