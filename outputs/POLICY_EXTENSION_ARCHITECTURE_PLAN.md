# 정책 확장 구조 개선 계획

## 1. 문서 목적

가까운 미래에 다양한 PR 병합 정책과 같은 정책의 여러 설정 변형을 반복적으로 추가할 수 있도록 현재 구조를 개선한다.

이 작업은 아래 네 가지 우려사항을 하나의 일관된 리팩터링으로 해결한다.

1. 정책 등록 지점 분산
2. 3개 정책 고정 UI 및 저장 스키마
3. 정책 인스턴스 식별자 부재
5. 정책 계약 테스트 부족

우려사항 번호는 논의 당시의 전체 목록을 유지한다. 4, 6, 7, 8은 이 문서의 구현 범위가 아니다.

## 2. 선행 조건

`outputs/REPLAY_EXPERIMENT_SNAPSHOT_FIX_PLAN.md`의 작업이 먼저 완료되어야 한다.

정책 구조가 바뀐 뒤에도 Replay는 다음 원칙을 유지해야 한다.

- 현재 편집 상태가 아니라 완료된 `ExperimentResult`의 시나리오와 정책 인스턴스를 사용한다.
- 선택한 결과와 Replay 입력을 배열 위치만으로 느슨하게 연결하지 않는다.
- Replay 반복 번호의 현재 기본값은 `0`이다.

## 3. 현재 구조와 문제

### 3.1 정책 등록 정보가 분산되어 있다

새 정책을 추가할 때 다음 위치를 함께 수정해야 한다.

- `src/sim/model.ts`: `PolicyConfig`, 기본 정책, 라벨
- `src/sim/policies.ts`: 구현과 `createPolicy` 분기
- `src/storage/schema.ts`: 정책 설정 검증
- `src/ui/ScenarioEditor.tsx`: 설정 행과 입력 컴포넌트
- 테스트와 벤치마크 fixture

정책의 종류, 기본 설정, 라벨, 검증 규칙, 생성 방법이 하나의 정의로 연결되지 않아 누락과 불일치 가능성이 높다.

### 3.2 UI와 가져오기 스키마가 세 정책에 고정되어 있다

- `ScenarioEditor`는 세 행을 직접 렌더링하고 `policies[1]`, `policies[2]`를 참조한다.
- `importSchema`는 정책 배열에 `.max(3)`을 적용한다.
- 결과 카드는 3열 및 세 가지 강조색을 전제로 한다.
- 사용자가 비교 정책을 추가, 제거, 복제하거나 순서를 바꿀 수 없다.

### 3.3 정책 종류와 정책 인스턴스를 구분하지 않는다

현재 `PolicyConfig.kind`가 알고리즘 종류와 비교 항목의 식별자 역할을 동시에 한다. 같은 종류의 정책을 설정만 달리해 두 개 이상 비교하면 다음 문제가 생긴다.

- React key 충돌
- 결과와 Replay 대상의 모호성
- CSV에서 설정 변형 구분 불가
- 사용자 정의 이름이나 비교 목적을 표현하기 어려움

### 3.4 공통 정책 계약을 자동 검증하지 않는다

개별 엔진 테스트는 존재하지만 모든 등록 정책에 같은 불변 조건을 적용하는 테스트 묶음은 없다. 정책 수가 늘면 잘못된 PR 선택, 비결정성, CI 중첩, 종료 상태 위반 같은 문제가 정책마다 반복될 수 있다.

## 4. 목표 구조

### 4.1 정책 종류와 비교 인스턴스를 분리한다

개념적으로 다음 두 계층을 구분한다.

```ts
type PolicyConfig =
  | SequentialConfig
  | BatchSplitConfig
  | LlmAssistedConfig;

interface PolicyInstance {
  id: string;
  name?: string;
  config: PolicyConfig;
}
```

- `kind`: 어떤 알고리즘 구현을 사용할지 식별
- `id`: 한 실험 안의 비교 항목을 고유하게 식별
- `name`: 필요한 경우 사용자가 설정 변형을 이해하기 위한 표시 이름
- `config`: 정책 알고리즘의 매개변수

정확한 타입 이름과 `name`의 필수 여부는 구현 시 결정할 수 있지만, 종류와 인스턴스 식별자를 분리한다는 원칙은 유지한다.

정책 ID는 다음 성질을 가져야 한다.

- 한 정책 목록 안에서 고유하다.
- 복제한 정책에는 새 ID가 부여된다.
- JSON 저장과 실험 결과에서 보존된다.
- 엔진 난수 시드와 난수 소비 순서에는 영향을 주지 않는다.
- 정책 알고리즘이 관측할 수 있는 정보로 전달되지 않는다.

### 4.2 중앙 정책 레지스트리를 둔다

각 정책 종류가 요구하는 정보를 하나의 정의에 가깝게 모은다.

```ts
interface PolicyDefinition<C extends PolicyConfig> {
  kind: C["kind"];
  label: string;
  description: string;
  defaultConfig: C;
  create(config: C): MergePolicy;
  // 설정 검증 및 UI 입력 명세는 구현 설계에 따라 연결한다.
}
```

레지스트리는 최소한 다음 소비자들의 단일 기준이 되어야 한다.

- 정책 구현 생성
- 표시 라벨과 설명
- 기본 설정 생성
- 지원 정책 목록
- 저장 입력 검증
- 동적 정책 설정 UI
- 정책 계약 테스트 대상 열거

React 컴포넌트를 시뮬레이션 코어 레지스트리에 직접 넣지 않는다. UI는 순수한 정책 메타데이터 또는 별도의 UI 어댑터를 사용해 코어의 UI 비의존 경계를 유지한다.

정책 구현 파일은 정책 수가 늘어도 한 파일이 비대해지지 않도록 종류별 모듈로 분리할 수 있다. 다만 파일 분리는 레지스트리의 단일 진입점보다 우선하지 않는다.

### 4.3 정책 목록 UI를 데이터 기반으로 만든다

설정 UI는 고정된 배열 인덱스 대신 `PolicyInstance[]`를 순회한다.

필수 기능은 다음과 같다.

- 등록된 정책 종류에서 비교 정책 추가
- 정책 인스턴스 제거. 단, 실험에는 최소 한 개를 유지
- 같은 종류의 정책을 여러 번 추가
- 각 인스턴스의 지원 설정 편집
- 인스턴스 ID를 React key로 사용
- 정책 수와 무관한 번호 및 레이아웃 렌더링

정책 순서 변경과 사용자 지정 이름 편집은 구현 복잡도에 따라 함께 제공할 수 있지만, 고유 ID와 설정 변형을 구분할 수 있는 표시는 반드시 제공한다.

### 4.4 정책 수 제한과 성능 보증을 분리한다

저장 스키마와 UI에서 “정확히 세 종류” 또는 “최대 세 인스턴스”라는 구조적 제한을 제거한다. 최소 한 개 정책 조건은 유지한다.

이 변경은 성능 개선 작업이 아니다. 저장소의 성능 예산인 “PR 1,000개, 정책당 100회, 정책 3개 비교, 30초 이내”는 대표 벤치마크 조건으로 유지한다. 정책을 더 많이 선택하면 실행량이 선형 증가할 수 있으며, 워커 병렬화는 이번 범위가 아니다.

### 4.5 공통 정책 계약 테스트를 만든다

레지스트리에 등록된 모든 기본 정책 정의를 자동으로 순회하는 공통 테스트를 추가한다.

계약 테스트는 공개된 정책 인터페이스와 엔진 이벤트 로그를 기준으로 최소한 다음을 확인한다.

- 같은 시나리오, 정책 설정, 반복 번호에서 결과가 결정론적이다.
- 정책이 사용할 수 없는 PR이나 종료 상태 PR을 CI에 제출하지 않는다.
- 한 시점에 단일 CI 자원만 사용한다.
- 한 결정에서 둘 이상의 CI 배치를 제출하지 않는다.
- CI 성공 배치만 머지되고 단독 CI 실패를 거친 PR만 격리된다.
- LLM 판단만으로 PR이 격리되지 않는다.
- 숨겨진 결함 정보나 미래 난수가 정책 인터페이스에 추가로 노출되지 않는다.
- 기본 정책 설정의 실행이 `policyError`로 끝나지 않는다.
- 결과 지표가 이벤트 로그에서 계산된다는 기존 경계를 유지한다.

정책별 고유 알고리즘의 정확성은 각 정책 모듈의 단위 테스트로 별도 검증한다. 공통 계약 테스트가 특정 정책의 처리 순서나 성능 우열을 강제하지 않도록 한다.

## 5. 포함 범위

### 우려사항 1: 정책 등록 지점 분산

- 중앙 정책 레지스트리 또는 동등한 단일 등록 진입점 도입
- 정책 라벨, 기본 설정, 생성, 검증, UI 메타데이터의 연결
- 신규 정책 추가 절차를 테스트 또는 문서로 고정
- 알 수 없는 `kind`에 대한 명시적인 실패와 빠짐없는 분기 처리

### 우려사항 2: 3개 정책 고정 UI 및 저장 스키마

- `policies[1]`, `policies[2]` 같은 위치 기반 편집 제거
- 정책 목록 동적 렌더링
- 추가, 제거, 동일 종류 복제 지원
- `.max(3)` 제거
- 결과 카드와 산점도의 임의 정책 수 렌더링
- 세 인덱스에 고정된 색상과 레이아웃 일반화
- 요구사항 문서의 “3개 정책”을 제품 제한과 성능 기준으로 구분하여 갱신

### 우려사항 3: 정책 인스턴스 식별자 부재

- 정책 인스턴스 ID 도입 및 고유성 보장
- 설정, Worker 요청, 실험 결과, JSON, Replay에서 ID 보존
- React key와 Replay 대상 선택에 ID 사용
- CSV에서 같은 종류의 설정 변형을 구분할 수 있도록 ID와 충분한 설정 정보 제공

### 우려사항 5: 정책 계약 테스트 부족

- 모든 등록 정책을 자동 열거하는 계약 테스트 추가
- 신규 정책이 레지스트리에 등록되면 계약 테스트 대상에 자동 포함
- 기존 세 정책의 알고리즘별 테스트 유지 또는 보강

## 6. 명시적 제외 범위

### 우려사항 4: 특정 정책에 종속된 정책 인터페이스

이번 작업에서는 `callLlm`, `onLlmCompleted`, `allowLlm`을 일반 분석기 인터페이스로 바꾸지 않는다. 중앙 레지스트리와 정책 인스턴스 구조는 현재 `MergePolicy` 인터페이스 위에 구축한다. 새로운 정책 요구가 현재 행동 집합으로 표현되지 않을 때 별도 작업으로 일반화한다.

### 우려사항 6: 정책 수 증가에 따른 실행시간 증가

다중 Worker 병렬화, 실행 스케줄링 최적화, 예상시간 계산은 구현하지 않는다. 기존 성능 예산과 벤치마크 조건은 유지한다.

### 우려사항 7: Replay와 실험 설정 불일치

이 문서의 선행 작업에서 완료한다. 이 리팩터링은 수정된 Replay 불변 조건을 보존하고 ID 기반 선택으로 강화한다.

### 우려사항 8: 정책 설정 버전 및 마이그레이션 부재

범용 정책 버전 체계나 마이그레이션 프레임워크를 도입하지 않는다. 다만 이번 변경으로 데이터 형태에 ID 계층이 추가되므로, 바로 이전의 현재 v1 `PolicyConfig[]` 데이터를 새 형태로 읽기 위한 최소한의 일회성 정규화는 허용한다. 이는 일반화된 마이그레이션 시스템으로 확장하지 않는다.

그 밖에 다음도 제외한다.

- 시뮬레이션 규칙 변경
- CI 성공·실패에 따른 자동 머지·격리 규칙 변경
- 정책에 숨겨진 결함, 상호작용 집합, 후보 master 실제 상태 또는 미래 난수 공개
- LLM 판단만으로 격리 허용
- 서버, 로그인, 중앙 데이터베이스 추가
- 정책 자동 추천 또는 우열 자동 판정

## 7. 데이터 및 경계 설계 원칙

### 7.1 엔진은 정책 인스턴스 메타데이터와 알고리즘 설정을 구분한다

엔진은 실행에 필요한 `PolicyConfig`만 정책 구현에 전달한다. 인스턴스 ID와 표시 이름은 실험 조율, 결과 연결, 저장, UI를 위한 메타데이터이며 정책 결정에 영향을 주지 않는다.

### 7.2 공정성과 재현성을 유지한다

같은 `ScenarioConfig`와 repetition에서는 모든 정책 인스턴스가 같은 숨겨진 세계를 사용한다. 인스턴스 ID를 난수 시드에 섞지 않는다. 같은 종류와 같은 설정의 두 인스턴스는 같은 repetition에서 동일한 결과를 내야 한다.

정책 인스턴스 배열의 순서를 바꾸거나 다른 정책 인스턴스를 추가해도 기존 인스턴스의 난수 결과가 바뀌지 않아야 한다.

### 7.3 UI 메타데이터가 코어를 UI에 의존시키지 않는다

정책 레지스트리의 코어 부분은 React나 브라우저 DOM을 import하지 않는다. 설정 필드 표현이 필요하면 순수 데이터 명세 또는 UI 계층의 어댑터를 사용한다.

### 7.4 저장 입력은 실행 전에 검증한다

정책 인스턴스 배열에 대해 다음을 검증한다.

- 최소 한 개
- ID가 비어 있지 않음
- 배열 내 ID 고유성
- 등록된 정책 `kind`
- 해당 정책 정의의 설정 제약조건

실험 실행 경로도 유효하지 않은 정책 인스턴스가 Worker까지 전달되지 않도록 시나리오와 정책 목록을 함께 검증해야 한다.

- `src/sim/model.ts`

  - 정책별 구현 분리와 등록 정의
- 신규 정책 레지스트리 모듈

  - 정책 인스턴스별 실행 및 결과 연결
- `src/worker/protocol.ts`, `src/worker/client.ts`, `src/worker/simulation.worker.ts`

## 9. 단계별 구현 계획

### 단계 1: 현재 동작 보호

1. 기존 세 정책의 기본 설정 결과와 결정론 테스트를 확인한다.
2. 정책 순서가 난수 결과에 영향을 주지 않는다는 테스트를 추가하거나 기존 구조에서 확인한다.
3. 선행 Replay 수정의 회귀 테스트가 통과하는지 확인한다.

### 단계 2: 정책 인스턴스 모델 도입

1. 정책 종류 설정과 비교 인스턴스 타입을 분리한다.
2. 기본 정책 목록에 안정적인 고유 ID를 부여한다.
3. 실험 결과가 인스턴스 ID를 보존하도록 타입과 실행 조율 계층을 변경한다.
4. 같은 `kind`를 여러 번 포함하는 타입 및 실행 테스트를 추가한다.

### 단계 3: 중앙 정책 레지스트리 구축

1. 기존 세 정책을 레지스트리 정의로 옮긴다.
2. 정책 생성, 라벨, 설명, 기본 설정이 레지스트리를 사용하게 한다.
3. 저장 검증과 UI 설정 메타데이터를 레지스트리에 안전하게 연결한다.
4. 등록되지 않은 종류는 암묵적으로 다른 정책으로 처리하지 않고 명시적으로 실패하게 한다.

### 단계 4: 저장 및 Worker 경계 변경

1. 정책 인스턴스 목록 스키마와 ID 고유성 검증을 추가한다.
2. 세 개 최대 제한을 제거한다.
3. 현재 v1 `PolicyConfig[]`를 새 인스턴스 형태로 정규화하는 최소 호환 경로를 결정하고 테스트한다.
4. Worker 요청과 응답, JSON, IndexedDB, CSV에서 정책 ID가 유지되는지 검증한다.

### 단계 5: 정책 설정 UI 일반화

1. 등록 정책 선택 및 추가 UI를 만든다.
2. 인스턴스별 설정 편집과 제거를 구현한다.
3. 같은 정책 종류의 복제를 허용하고 새 ID를 생성한다.
4. 고정 배열 인덱스 참조를 제거한다.
5. 실행 전 시나리오와 정책 목록을 함께 검증한다.

### 단계 6: 결과 및 Replay UI 일반화

1. 정책 ID를 React key와 결과 연결에 사용한다.
2. 결과 카드와 산점도가 임의 개수 정책을 렌더링하도록 한다.
3. 고정 세 색상 이후에도 구분 가능한 시각 규칙을 적용한다.
4. Replay가 결과의 정책 인스턴스 ID로 정확한 설정을 선택하는지 검증한다.

### 단계 7: 정책 계약 테스트 구축

1. 레지스트리의 모든 기본 정책을 순회하는 테스트 도우미를 만든다.
2. 공통 불변 조건을 이벤트 로그와 결과로 검증한다.
3. 같은 종류의 복수 인스턴스와 순서 변경 사례를 검증한다.
4. 새 정책 등록 시 계약 테스트 대상에서 빠질 수 없는 구조인지 확인한다.

### 단계 8: 문서와 전체 검증

1. 요구사항 문서의 정책 개수 제한을 갱신한다.
2. 신규 정책 추가 절차를 레지스트리 기준으로 기록한다.
3. 필수 검증을 모두 실행한다.
4. 우려사항 1, 2, 3, 5 각각에 대해 구현과 테스트를 대조 보고한다.

## 12. 구현 시 미결정 사항

다음은 구현 전에 현재 UI와 저장 요구를 기준으로 최종 결정한다.

1. `PolicyInstance.name`을 필수로 둘지, 자동 라벨만 제공할지
2. 정책 설정 폼을 순수 메타데이터로 생성할지, 정책 종류별 UI 어댑터를 둘지
3. 사용자가 정책 순서를 직접 변경할 수 있게 할지
4. 이전 v1 정책 배열에 생성할 ID를 결정적으로 만들지, 최초 정규화 시 UUID를 부여할지
5. 임의 정책 수의 색상을 팔레트 순환으로 표현할지, CSS 변수나 색상 생성 규칙을 사용할지

이 결정들은 정책 알고리즘이나 시뮬레이션 규칙을 바꾸어서는 안 된다.

## 13. 구현 결과

이 계획은 완료되었다.

- 정책 비교 단위는 `PolicyInstance { id, config }`로 분리했다. 사용자 지정 이름은 도입하지 않고 레지스트리의 자동 라벨로 설정 변형을 표시한다.
- 정책 설정 UI는 레지스트리의 순수 숫자 필드 메타데이터로 생성하며 React 컴포넌트는 코어 레지스트리에 포함하지 않는다.
- 정책 순서 변경은 제공하지 않고 추가·제거·복제를 제공한다.
- 이전 v1 `PolicyConfig[]`에는 배열 위치와 kind를 사용한 결정적 ID를 부여한다. 범용 마이그레이션 프레임워크는 도입하지 않았다.
- 결과 카드와 산점도 색상은 인덱스 기반 HSL 생성 규칙을 사용한다.
- 우려사항 4의 LLM 전용 정책 인터페이스, 우려사항 6의 실행 병렬화, 우려사항 8의 범용 버전 체계는 변경하지 않았다.
